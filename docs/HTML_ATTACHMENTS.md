# Offline HTML attachments

A PDF opened in Thoughts can link to an HTML attachment that is downloaded with its source generation and opened in the default browser without an internet connection.

On desktop, use **Import HTML…** on a source project's Library menu (or its Documents group). The importer saves a private blob copy and queues it for object upload on Sync. The small project manifest records its stable logical path, hash, and byte count. HTML bytes never enter editable source reconciliation or source Git history; placing files in the source tree does not publish them.

For example, after importing `plot.html` into `docs-example`, put this in the document source:

```tex
\href{thoughts-html:docs-example/tex/support/html/plot.html}{Open interactive plot}
```

Build and Sync the project, then Sync the receiving device. The HTML is pinned by its SHA-256 in the PDF's immutable source artifact and downloaded using the existing resource transfer mechanism. Clicking the link opens the installed attachment even after local PDF annotations change the PDF bytes. A missing or damaged attachment produces an explicit message asking you to Sync.

Use one UTF-8 `.html` file, no larger than 100,000,000 bytes (100 MB), with its scripts, styles, images, fonts, and data embedded. Filenames use letters, digits, dots, underscores, and hyphens and start with a letter or digit. External resources, network requests, frames, forms, and browser storage are unavailable in the isolated page. Inline JavaScript, CSS, data images, and downloads are supported. This version does not import folders of web assets or implement HTML editing on Android.

Each opened page receives its own loopback origin and unguessable URL. The HTTP server binds only to `127.0.0.1`; it never publishes the document to the network. The browser receives only the selected HTML bytes, not access to the project folder. Android displays an **Offline HTML** notification with **Close pages**, which stops its foreground service and invalidates opened URLs. Up to 16 Android pages can remain open. On desktop, pages remain available while Thoughts is running, for up to 12 hours; reopen their PDF links afterward. Reloading an already open page does not pull a newer attachment version: reopen the PDF link after Sync.

The custom PDF link is handled by Thoughts. Other PDF viewers will not automatically resolve it. Sync updates to the server and both clients must be installed before publishing HTML-bearing document generations.

## Pages of a folder

Since capability `html_pages_v1` every device keeps a folder's pages in step: a page added on Fedora
(the connector's `add_html_page`, `POST /v1/html-pages`) is installed into the Mac's folder by its next
Sync, and a page the Mac's folder gains or changes is added to the folder's list. The list is the
manifest above; Fedora alone writes it. See `protocol/html-pages.md`.

## Review cards in attachments

Capability `html_attachment_cards_v1`. Clients offer **New review card** inside an attachment page only when the server advertises it.

A card made from a text selection inside an attachment page is anchored by the text it remembers and the page state, not by source markers: attachment text is often generated by the page's own scripts, so markers in the file cannot reach it. This is the one exception to always-linked cards. Its `primary` has no `page`, `rect`, `regions` or other PDF geometry, and none is ever guessed:

```json
{"document_id": "<owner document id>", "pdf_stem": "ideas", "pdf_sha256": "<PDF the link was in>",
 "created_in": "html_attachment",
 "html_attachment": {"path": "docs-ideas/tex/support/html/explainer.html", "sha256": "<attachment sha256>"},
 "text_quote": {"exact": "…", "prefix": "…", "suffix": "…"},
 "page_state": {"hash": "#simulator"},
 "selected_text": "…", "question": "…"}
```

The card payload has `source_authority: "client-v1"` and `source_link: {"state": "html_attachment"}`, a terminal state.

- **Owner.** The document whose PDF link opened the page (`pdf_stem`, `document_id`). The card is listed and reviewed with that document, like every card. A move to another document of the same Project needs no markers.
- **Validation** (`schemas.HtmlAttachmentSelection`, HTTP 422). `html_attachment.path` follows the source-closure rule for `html_attachment` resources (`docs-<folder>/tex/support/html/<file>.html`, or an HTML file in the folder's `tex/` or `markdown/` tree). `html_attachment.sha256` and `pdf_sha256` are lowercase SHA-256 hashes and `pdf_stem` is required. `text_quote` is the HTML view's quote (`exact` with visible text, `prefix`/`suffix` up to 200 characters; clients send up to 64). `page_state` is optional, and `page_state.hash` is `""` or a `location.hash` starting with `#`, at most 512 characters. The primary must not have `page`, `rect`, `regions`, `source_anchor`, `source_range`, `html_edition_sha256`, `component_origin`, `answer_region_override` or `scope: "document"`. The payload must not have `source_change`. `created_in` is either absent (PDF view), `html` (HTML view) or `html_attachment`, and any other value is refused. `source_link.state = "html_attachment"` is valid only on such a card. A comment cannot be made in an attachment yet.
- **Attachment version** (HTTP 409, `error_code: "html_attachment_unknown"`). When the server knows the owner PDF, `(path, sha256)` must be one that PDF can link to. That means an `html_attachment` resource of the owner's current publication (`source_resources`), a resource of the exact PDF the card names (its source artifact, also for an older PDF version), or an entry in any version of the attachment manifest of the path's folder (`tex/support/thoughts_html_attachments.txt`, current file and revision log). The check runs when the card is made and whenever its owner or attachment changes. A later edit (tags, sliders, a note) is never refused because the attachment changed since. The client keeps the card and asks the user to Sync and reopen the attachment from its PDF.
- **Never linked.** Source linking (`review_source_link.eligible`, `repair_candidate`, `prepare_link`, `process_source_link`), publication reanchoring (`review_reanchor.project_review_anchors_for_publication`, `queue_review_reanchors_for_publication`, the reanchor worker) and the first-area page fingerprint skip these cards. The server never queues them, never inserts markers, never adds PDF geometry and never marks them `needs_attention`. A stray job for one goes `stale`.
- **Retention.** `pdf_retention` counts `primary.html_attachment.sha256` of every card as a referenced object (`CARD_ATTACHMENT_PATHS`), as feedback stamps pin PDFs. The attachment version a card was made on therefore stays, so a client can open it if the current version no longer contains the text. Retention retires only superseded PDFs and their HTML editions today, so this keeps the pin explicit for any later object cleanup.
- **Reviews.** The client opens the owner's current attachment at `path` (falling back to the card's `sha256` while that object is cached), restores `page_state.hash`, waits for the page to settle and masks `text_quote`. If the text is no longer in the page, the client shows "Answer not found in the current page" and the stored answer text instead of a mask.

SDKs: Kotlin `HtmlAttachmentCardPrimary` (`toJson`, `fromJson`, `applyTo`), `HTML_ATTACHMENT_CARDS_CAPABILITY`, `HTML_ATTACHMENT_UNKNOWN`, `HealthResponse.supportsHtmlAttachmentCards()`, `ServerException.errorCode`. C++ `Thoughts::HtmlAttachmentCardsCapability`, `Thoughts::HtmlAttachmentUnknownError`.

## Validation

- Server: attachment discovery, closure verification, publication, object identity, path validation, transfer contract, and existing source regressions. Cards in attachments: `tests/test_html_attachment_cards.py`, covering shape, version check, linking and reanchor exemption, retention, listing and move.
- Desktop: link parser, loopback HTTP behavior, manifest and object verification, local annotation compatibility, and existing Library/style regressions.
- Android: downloaded object retrieval after restart, corrupt/missing/wrong-document rejection, loopback HTTP responses, and sandbox browser handoff with an interactive button.

## Fedora installation

HTML attachments are part of the server; they are installed with every regular Fedora deployment (`deploy/fedora/install-native.sh`, see `deploy/fedora/README.md`).

HTML upload, download, verification, renderer materialization, and local browser serving use file streams. Fedora’s periodic source synchronization handles only the small reference manifest; it does not scan, diff, or republish HTML bytes. Existing `thoughts-html:` links retain their logical path.
