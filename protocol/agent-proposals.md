# Agent proposals in sources

Status: §1–§9, §11 and §12 normative, version 1 (2026-10-10; LaTeX metadata with both `created` and `conversation_id` mandatory since the same day; optional `conversation_url` since 2026-10-18; move pairs §12 since 2026-11-11); §10 proposed (phase 2, not yet implemented). Fixtures: `fixtures/agent-proposals/cases.json` (generated by `gen_cases.py` next to it) and, for §10, `fixtures/agent-proposals/decisions.json` (generated by `gen_decisions.py`). Conformance runners: `tools/proposal-conformance/`.

An agent proposal is a pending source edit stored inside a LaTeX or Markdown source file.
The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.
Every reader (server, desktop, Android, VS Code) MUST produce the same proposals, issues and decision outputs as the fixtures.

## 1. Model

A parsed source yields a list of **proposals** and a list of **issues**, both in source order.

| field | meaning |
|---|---|
| `id` | stable ID (§3.1) |
| `created_at` | creation timestamp (§3.2) |
| `conversation_id` | lowercase UUID (§3.3) |
| `conversation_url` | optional link to the conversation (§3.6); absent when not written |
| `explanation` | why the edit is proposed (§3.4) |
| `original` | the source text the wrapper replaces on reject |
| `replacement` | the source text the wrapper replaces on accept |
| `span` | `[start, end)` of the whole wrapper (§3.5) |

An issue is `{code, span, id?}` (§6). `id` is present whenever the wrapper's ID text was read, even if it is invalid.
No history is part of this model: a resolved proposal simply disappears from the source. Whether a disappearance was a decision is not visible in the source; §10 defines how the server learns it.

## 2. Format selection

The parser MUST be chosen by the file extension, case-insensitively: `.tex` is LaTeX; `.md` and `.markdown` are Markdown.
Content MUST NOT select the parser: a `.tex` file containing Markdown marker text has no Markdown proposals, and a `.md` file containing `\agentProposedEdit{...}` has no proposal and no issue.
Other files have no proposals.

## 3. Common rules

### 3.1 ID

`id` MUST match `[a-z0-9][a-z0-9._:-]{0,127}` (ASCII, 1–128 characters).
In LaTeX the ID argument is trimmed of ASCII whitespace (space, tab, LF, CR, FF, VT) before validation; Markdown IDs are not trimmed.
IDs MUST be unique within a file (§6, `duplicate_id`). Writers MUST also make them unique across the workspace at creation (§8).

### 3.2 Timestamp

`created_at` MUST match `YYYY-MM-DDTHH:MM:SS[.F]Z` where every digit is ASCII, `T` and `Z` are uppercase, and `.F` is 1–9 digits.
It MUST denote a real UTC instant: year 0001–9999, month 01–12, a day that exists in that month (Gregorian leap years), hour 00–23, minute 00–59, second 00–59.
Offsets (`+02:00`), lowercase `t`/`z`, missing zone, date-only values and leap seconds are invalid.
Readers MUST return the value exactly as written (no normalization). Writers MUST emit `YYYY-MM-DDTHH:MM:SS.mmmZ` (UTC, exactly 3 fractional digits).
The rule is the same for LaTeX metadata and both Markdown versions.

### 3.3 Conversation ID

A structured conversation ID (`conversation_id=` in LaTeX metadata, the `conversation_id:` header in Markdown, the JSON member in Markdown v1) MUST match `[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}` (lowercase).
Every proposal has both a timestamp and a conversation ID, in both formats; a wrapper or block without either is `invalid_metadata`.
There is no fallback: a `Prepared in Codex conversation <UUID>.` sentence in the explanation is ordinary explanation text and does not supply a conversation ID (it was read before 2026-10-10).

### 3.4 Explanation

`explanation` MUST NOT be empty or ASCII whitespace only, in either format (`invalid_metadata`).
In LaTeX it is the second argument exactly as written: readers MUST NOT trim it, remove comments, or undo TeX escaping (`50\% done` stays `50\% done`; the desktop writer's trailing newline stays).
A client MAY display it with the writer's escape table (§8.1) reversed, but MUST NOT store that rendering.
In Markdown it is the decoded header block (§5.2).

### 3.5 Text, offsets and line endings

Sources are UTF-8. Offsets in this spec and in the fixtures are Unicode code points of the decoded text; a U+FEFF at the start is an ordinary code point.
Implementations MAY use UTF-16 or byte offsets internally but MUST convert when they exchange offsets with each other.
`original`, `replacement`, `explanation` and spans are exact substrings or decodings: CR characters are preserved. Line-ending rules are format specific (§4.1, §5.4).

### 3.6 Conversation link

`conversation_url` is OPTIONAL. It lets a reviewer open the conversation that wrote the proposal.
When present it MUST be exactly one of:

- `https://claude.ai/code/session_<s>` where `<s>` is 1–64 ASCII letters or digits (a Claude Code session, opened in the Claude app or a browser);
- `codex://threads/<uuid>` with a lowercase UUID as in §3.3 (a Codex thread, which only opens on the computer that ran it).

Any other value, including an empty one, is `invalid_metadata`. A proposal without the link is complete; readers report it as absent (no field), not as an empty string.
Writers SHOULD add the link when they know it and MUST NOT invent one; clients MUST open it only after checking it against this rule.

## 4. LaTeX

### 4.1 Lexical rules

- A character is **escaped** when it is immediately preceded by an odd number of consecutive backslashes. `\%` is a literal percent sign; `\\%` is a line break followed by a comment; `\\\%` is a line break followed by a literal percent sign.
- An unescaped `%` starts a **comment** that ends after the next LF (or at end of file). A CR before the LF belongs to the comment.
- Inside a braced argument, a backslash consumes itself and the next character (so `\{`, `\}`, `\%`, `\\` never count as delimiters); unescaped `{` and `}` nest; comments are skipped.
- A **control word** is a backslash followed by the longest run of `[A-Za-z@]`.

### 4.2 Live occurrences

A wrapper is the control word `\agentProposedEdit` at a position that is **live**. A position is not live when it is:

1. part of a different control word (`\agentProposedEditAfter`, `\agentProposedEdit@impl`), or preceded by an escaping backslash (`a\\agentProposedEdit{...}` is a line break followed by text);
2. inside a comment;
3. inside a verbatim region: from an unescaped `\begin{ENV}` (spaces or tabs MAY precede `{`) to the first following literal `\end{ENV}`, or to end of file, for ENV in `verbatim`, `verbatim*`, `Verbatim`, `Verbatim*`, `BVerbatim`, `BVerbatim*`, `LVerbatim`, `LVerbatim*`, `lstlisting`, `minted`, `DocCode`; or inside `\verb<d>…<d>`, `\verb*<d>…<d>` or `\lstinline<d>…<d>` where `<d>` is the character right after the command (not whitespace, a letter, `[` or `{`) and the closing `<d>` is on the same line. A `\begin{...}` inside a comment does not open a region. Other environments, including the user's `LinkedDocCode` (which sets `commandchars=\\\{\}` and therefore executes commands), are ordinary TeX;
4. a **definition**: the command is immediately preceded, ignoring ASCII whitespace, by an optional `{`, an optional `*`, and an unescaped control word from `\def \gdef \edef \xdef \let \newcommand \renewcommand \providecommand \DeclareRobustCommand \NewDocumentCommand \RenewDocumentCommand \ProvideDocumentCommand \DeclareDocumentCommand \newrobustcmd \renewrobustcmd \providerobustcmd` (this covers `\global\let\agentProposedEdit\relax`, `\providecommand\agentProposedEdit[5][]{#5}` and `\let\agentProposedEdit\agentProposalPdfText%`);
5. a **mention**: after the name and any whitespace and comments, the next character is neither `{` nor `[`.

Positions that are not live produce neither proposals nor issues.

### 4.3 Wrapper grammar

```
\agentProposedEdit [ METADATA ] {ID}{EXPLANATION}{ORIGINAL}{REPLACEMENT}
```

- Whitespace and comments MAY appear between the name, the metadata and the arguments.
- `[ METADATA ]` is REQUIRED. It runs to the first `]`. Its content, trimmed of ASCII whitespace, MUST be exactly `created=<timestamp>,conversation_id=<uuid>`, optionally followed by `,conversation_url=<link>` (§3.6), with no other whitespace, keys or order (`invalid_metadata`). A wrapper with no metadata (written before 2026-10-10 as a legacy form), or with only `created=` or only `conversation_id=`, is `invalid_metadata`: it is reported like any broken wrapper, cannot be decided, and does not affect other proposals in the file.
- Exactly four braced arguments follow. The span runs from the backslash to the closing brace of the fourth argument.

Example (the shape the desktop writes):

```tex
\agentProposedEdit[created=2026-10-10T12:00:00.000Z,conversation_id=0b6c5b7e-1d2a-4c3b-9f8e-112233445566]{agent-1}{Clarify.
}{Old line.
}{New line.
}
```

yields `id=agent-1`, `explanation="Clarify.\n"`, `original="Old line.\n"`, `replacement="New line.\n"`.

### 4.4 Field mapping

`id` = argument 1 trimmed; `explanation` = argument 2; `original` = argument 3; `replacement` = argument 4 — all exact contents between the braces.
`created_at` and `conversation_id` come from the metadata (§3.2, §3.3); both are always non-empty. `conversation_url` comes from the metadata when written (§3.6).

### 4.5 Retired and unsupported forms

These are not proposals and not issues; readers MUST treat them as ordinary text (an unknown command, or verbatim text under §4.2), and writers MUST NOT create them:

- the retired removal wrapper `\agentRemove{…}{…}{…}`, with or without `\agentRemovedBlock` (no occurrences remain in real sources). Text inside a proposal argument that contains it is not nesting;
- the fancyvrb command-character forms `|agentProposedEdit(…)(…)(…)(…)` and `|agentRemove(…)(…)(…)` inside a `Verbatim`/`DocCode` with `commandchars=|\(\)`. Existing ones in Library sources are being converted to ordinary wrappers.

## 5. Markdown

### 5.1 Marker lines

A **marker line** is a line that begins at column 0 (start of file or after LF) with `<!-- thoughts:agent-proposal:`.
Only these four forms are valid, each terminated by LF:

```
<!-- thoughts:agent-proposal:v2:start
<!-- thoughts:agent-proposal:v2:end <id> -->
<!-- thoughts:agent-proposal:v1:start <base64url> -->
<!-- thoughts:agent-proposal:v1:end <id> -->
```

Any other marker line (unknown version, trailing CR, missing LF at end of file, extra text) is `malformed_marker`.
Text that does not start a line is never a marker (documentation shows markers indented or inline).

### 5.2 Version 2 block

```
<!-- thoughts:agent-proposal:v2:start
id: agent-1
created_at: 2026-10-10T12:00:00.000Z
conversation_id: 0b6c5b7e-1d2a-4c3b-9f8e-112233445566
explanation:
| Clarify.
original_text:
| Old line.
| 
-->
New line.
<!-- thoughts:agent-proposal:v2:end agent-1 -->
```

- The **header** is the lines after the start line up to the first line that is exactly `-->`. If there is none, the block is `unclosed_group` (an HTML comment running to end of file).
- Header lines, in this order and nothing else: `id: <id>`, `created_at: <timestamp>`, `conversation_id: <uuid>`, an optional `conversation_url: <link>` line (§3.6), an optional ignored `replacement_length: <anything>` line, `explanation:` followed by zero or more `| ` lines, `original_text:` followed by zero or more `| ` lines.
- A block value is its `| ` lines with the two-character prefix removed, joined with LF; `--&gt;` is replaced by `-->` and then `&amp;` by `&`. So `original_text` `"a\n"` is written `| a` + `| ` (one empty line), and `""` is written with no lines. A line `|` without the space ends the block and makes the header invalid.
- The **end marker** is the first line `<!-- thoughts:agent-proposal:v2:end <id> -->` after the header, where `<id>` is the header's `id:` value exactly. `replacement` is the text between the header's `-->` line and the end marker; the span runs from the start line to the end of the end marker line, LF included.

### 5.3 Version 1 block (legacy)

`<!-- thoughts:agent-proposal:v1:start <data> -->` LF, replacement, `<!-- thoughts:agent-proposal:v1:end <id> -->` LF.
`<data>` MUST be canonical unpadded base64url (`[A-Za-z0-9_-]+` that re-encodes to itself) of a UTF-8 JSON object with string members `id`, `created_at`, `conversation_id`, `explanation`, `original_text`, and optionally `conversation_url` (a string valid under §3.6, otherwise `invalid_metadata`); other members are ignored.
`created_at` and `conversation_id` are required and validated as in §3.2 and §3.3, exactly like v2: a missing, non-string or invalid value is `invalid_metadata` (unchanged by the 2026-10-10 rule, which only made the LaTeX metadata mandatory).
v1 and v2 IDs share one namespace. Readers MUST keep reading v1; writers MUST NOT create it.

### 5.4 Line endings

Marker lines and the header's `-->` line MUST end with LF; a CR before that LF makes the marker malformed, so a file converted wholesale to CRLF reports issues instead of silently losing its proposals.
CR inside `| ` lines and inside the replacement is content (this is what a writer produces in a CRLF file: LF marker lines around CRLF content).

### 5.5 Code blocks

Markdown structure is not interpreted: marker lines inside fenced or indented code blocks are live, because writers wrap arbitrary line ranges, including lines of a code block. To show a marker as an example, indent it or put it inline.

## 6. Issues

A broken wrapper produces exactly one issue; other proposals in the file stay valid and decidable. Codes:

| code | meaning | span |
|---|---|---|
| `unclosed_group` | LaTeX: an argument `{` or the metadata `[` is not closed before end of file. Markdown: a v2 header has no `-->` line. | wrapper start to end of file |
| `missing_argument` | LaTeX: fewer braced arguments than required | wrapper start to the end of the last complete argument (or metadata) |
| `malformed_marker` | Markdown: a marker line that is not one of the four forms | the line, LF included |
| `unmatched_marker` | Markdown: a start marker without its end marker, or an end marker no start consumed | start: start line through the header (v2 `-->` line, v1 start line); end: the line |
| `invalid_metadata` | LaTeX metadata missing or malformed (§4.3), Markdown header or v1 data, timestamp, conversation ID or link, or a blank explanation | the whole wrapper; a Markdown start whose ID cannot be read: start line through header |
| `invalid_id` | the ID does not match §3.1 | the whole wrapper |
| `nested_proposal` | a live wrapper (LaTeX, §4.2) or a marker line (Markdown) occurs inside the wrapper's arguments or replacement | the outer wrapper |
| `duplicate_id` | another wrapper in the file carries the same ID | each such wrapper |

Rules:

- When several codes apply to one wrapper, report the first in table order.
- Recovery: after a wrapper (complete or `missing_argument`) scanning resumes at the end of its span; after an unmatched Markdown start it resumes after its header. `unclosed_group` ends parsing: proposals before it stay valid; nothing after it is reported, because it belongs to the unclosed group (this is what TeX does too).
- Nesting: only the outermost wrapper is reported; wrappers inside it are neither proposals nor issues. Commented-out wrappers and mentions inside an argument are not nesting.
- Duplicates: every wrapper whose ID was read counts, including broken ones (a valid `p1` next to `\agentProposedEdit{p1}{w}{a}` is `duplicate_id`); orphan end markers carry their ID but do not count.
- A Markdown start whose ID is unreadable (no or empty `id: ` line, undecodable v1 data, non-string v1 `id`) cannot be paired, so its end marker is additionally reported as `unmatched_marker`.

## 7. Decisions

A decision is `accept` or `reject` for a non-empty set of IDs.

- Each ID MUST name exactly one valid proposal. Otherwise the whole decision is refused, nothing is written, and the refusal code is that of the first requested ID (in request order) that fails: the code of the first issue in source order carrying that ID, or `unknown_id` if none does (including IDs inside a nested wrapper or after an unclosed group).
- Output: each selected wrapper's span is replaced by exactly `replacement` (accept) or `original` (reject); all other text is unchanged byte for byte. No newline is added or removed: the Markdown end marker's LF is part of the span, and the LF before it is the end of the replacement.
- Issues elsewhere in the file MUST NOT block a decision.

```
Intro.\n\agentProposedEdit[…]{agent-1}{Clarify.\n}{Old line.\n}{New line.\n}Outro.\n
accept → Intro.\nNew line.\nOutro.\n      reject → Intro.\nOld line.\nOutro.\n
```

Partial decisions (accepting a prefix of a proposal; Android source editor only once §10 ships, which removes them from VS Code) are a client feature, not part of this format: the client computes an ordinary source edit that keeps a valid wrapper with the same ID, metadata and explanation around the undecided rest (or no wrapper). Markdown proposals support whole decisions only.

## 8. Writers

There are two writers, both clients: the desktop (`thoughtsctl create-proposal`, `create-proposals`, `revise-proposal`, `remove-proposal`) and the headless client `clients/thoughts-cli` (the same create and revise requests and results), which reads the source with `GET /v1/sources/{path}` and `GET /v1/objects/{sha256}`, checks uniqueness against every canonical source, and publishes the result with `POST /v1/source-publications` as its own device, like the Mac's source publisher. The server writes no proposals; it records and resolves them (sections 9 and 10). From 2026-10-27 until its removal the server also had a writer (`POST /v1/agent-proposal-authoring`); its request records remain in the table `agent_proposal_authoring`.

- Writers MUST create IDs matching §3.1 that occur nowhere else in the workspace (the desktop writes `agent-<uuid4>` and checks every source, including hidden files and snapshots).
- `created_at` per §3.2 (`.mmmZ`), `conversation_id` lowercase, `conversation_url` per §3.6 when known, explanation trimmed and non-blank.
- `original` is a range of whole lines of the current source; `original` and `replacement` MUST NOT contain a wrapper or marker (no nesting) and MUST NOT intersect an existing proposal.
- Writers MUST NOT create or revise proposals in generated sources; they refuse with `generated_source` ("This file is generated; change its generator or the generator's inputs instead of proposing an edit here."). A source is generated if its path relative to its folder (`docs-<name>/` or a Project's default folder) contains a `tex/generated/` segment, or if its first non-empty line starts with `% Generated artifact` or `% Generated by ` (Markdown: `<!-- Generated artifact` or `<!-- Generated by `). Withdrawing an existing proposal there stays allowed; reading and deciding proposals in generated sources is unchanged (§6, §7).

### 8.1 LaTeX

```
\agentProposedEdit[created=<ts>,conversation_id=<uuid>]{<id>}{<escaped explanation>\n}{<original>}{<replacement>}
```

With a link the metadata is `[created=<ts>,conversation_id=<uuid>,conversation_url=<link>]`.

The explanation is escaped character by character: `{ } % $ & # _` become `\{ \} \% \$ \& \# \_`; `\` becomes `\textbackslash{}`, `^` becomes `\textasciicircum{}`, `~` becomes `\textasciitilde{}`. `original` and `replacement` are TeX source and are not escaped; a writer MUST refuse them if their braces do not balance under §4.1 or if they end inside a comment (a trailing comment must include its LF).

### 8.2 Markdown

The v2 block of §5.2, with LF marker lines and the `conversation_url:` line only when there is a link. Block lines are encoded by replacing `&` with `&amp;` and then `-->` with `--&gt;`. A non-empty replacement that does not end with LF gets one, so the end marker starts a line.

## 10. Decisions and removed proposals

Status: proposed (phase 2). Nothing in this section is implemented yet; §10.9 says how it is rolled out.

### 10.1 Rule

A pending proposal is decided only through Thoughts:

| path | who writes the source | how the server learns the decision |
|---|---|---|
| phone Accept/Reject (PDF sheet, Overview); desktop Accept/Reject of a proposal whose source is not local | the server (`/v2/agent-proposal-resolutions`, worker) | the resolution job is the publication (§10.4.1) |
| desktop Accept/Reject (Library overview, PDF proposal card, multi-select) of a local source | the desktop, in its local file | a decision claim on the source upload (§10.4.2) |
| VS Code Accept/Reject (whole proposals only) | the desktop, asked by `thoughtsctl decide-proposal` (§10.7.3) | a decision claim, as for the desktop |
| phone source editor (whole or partial) | the phone, in its source draft | a decision claim on the phone's source save |
| agent withdrawal (MCP `remove_proposal`, `thoughtsctl remove-proposal`) | the desktop | a claim with action `withdraw` |
| Dismiss of a removed proposal (§10.6) | nobody (no source change) | an operation on the `proposal` entity |

Removing or replacing the markup any other way (a text editor, `git checkout`, a sed script, an agent editing the file, a merge, a lost file) is not a decision.
Thoughts cannot tell an acceptance from an accident, so such a proposal is kept as **removed outside Thoughts** until the user restores or dismisses it.
This mirrors comments whose source marker vanished ("Anchor removed", `scope.state = needs_attention`, `scope.reason = anchor_removed`).

### 10.2 States

The server's current-proposal entity (`entity_type = proposal`, collection `proposals`, entity ID = proposal ID) is the only authority. Its `payload.status`:

| status | `deleted` | meaning | shown |
|---|---|---|---|
| `pending` | false | a valid wrapper with this ID is in canonical source | as a proposal |
| `removed_outside` | false | the wrapper vanished from canonical source without a decision | under Issues, "Removed outside Thoughts", with Restore Proposal and Dismiss |
| `accepted`, `rejected`, `decided_in_parts`, `withdrawn`, `dismissed`, `document_deleted` | true | retired: decided (§10.4), dismissed (§10.6), or its document was removed from the Library | not shown |
| `deleted_from_source` | true | legacy retirement written before phase 2 (§10.10) | not shown |

`decided_in_parts` is a partial review whose last step removed the wrapper. A retired row stays server-side only so that a wrapper that reappears is recognised as `restored` (it becomes `pending` again); it is not history and carries no events.

Transitions, all made by the server inside the verified source transaction (§10.4.3) except Dismiss (§10.6):

```
(absent) --wrapper appears--> pending
pending --wrapper changes or moves--> pending
pending --wrapper vanishes + matching decision--> accepted | rejected | decided_in_parts | withdrawn
pending --wrapper vanishes, no decision--> removed_outside
removed_outside --matching decision arrives later (§10.4.3)--> accepted | rejected | decided_in_parts | withdrawn
removed_outside --wrapper reappears (Restore or any edit)--> pending
removed_outside --Dismiss--> dismissed
retired --wrapper reappears--> pending   (existing "restored")
```

"Vanishes" keeps today's conservative evidence rules (`reconcile_proposal_history`): the ID was the only valid wrapper with that ID in the previous verified revision of a source that took part in the transaction, and the ID text occurs nowhere in the resulting tree. A wrapper that became broken (an issue carrying the ID, §6), commented out, duplicated, or moved atomically to another file has not vanished.
A source file deleted together with its document (Library removal of the document, the comment rule of `_retiring_sources`) retires its proposals as `document_deleted`; deleting any other file is an ordinary disappearance.

### 10.3 Removed-proposal record

A `removed_outside` row keeps the last verified proposal and where it was:

```json
{
  "schema_version": 1,
  "proposal_id": "agent-1",
  "status": "removed_outside",
  "kind": "removed_outside",
  "snapshot": {"proposal_id": "agent-1", "source_file": "docs-x/tex/source/a.tex", "comment": "Clarify.\n",
               "before": "Old line.\n", "after": "New line.\n",
               "created_at": "2026-10-10T12:00:00.000Z", "conversation_id": "0b6c5b7e-1d2a-4c3b-9f8e-112233445566"},
  "source_file": "docs-x/tex/source/a.tex",
  "wrapper_sha256": "<sha256 of the wrapper text in the last revision that had it>",
  "removal": {
    "operation_id": "<source operation or publication that removed it>",
    "device_id": "<uploading device>",
    "removed_at": "2026-10-11T09:00:00.000Z",
    "source_line": 42,
    "before_sha256": "<source before>",
    "after_sha256": "<source after, or \"\" when the file was deleted>",
    "looks_like": "accept"
  },
  "deleted": false
}
```

- `wrapper_sha256` is the SHA-256 of the UTF-8 bytes of the wrapper's span (§1). The server writes it on every `pending` row too, so clients and claims can name an exact proposal version.
- `source_line` is the 1-based line of the wrapper's first character in `before_sha256`.
- `looks_like` is a hint for the user, never a decision: `accept` or `reject` when `after` equals §7's output for that ID (alone, or for all IDs removed from that file together), else `edited`; `file_deleted` when the file is gone.
- Leaving `removed_outside` drops `removal`, like `_left_anchor_removed` drops the anchor-removed keys of a comment.

### 10.4 Decision records

#### 10.4.1 Server-applied decisions

A phone decision is an `AgentProposalResolution` job; the worker publishes its source change with `publication_id = job.id`.
The reconciler already treats the job's `proposal_ids` and `action` as the decision for wrappers that vanish in that publication (`accept` → `accepted`, `disregard` → `rejected`). Nothing changes; an undo makes the wrappers reappear (`pending`).

#### 10.4.2 Decision claims

Every other decision is executed by a client that rewrites its own copy of the source. That client attaches a **decision claim** to the source upload that carries the change:

```json
{
  "decision_id": "6f1c…",                 // UUID v4, unique per claim
  "proposal_id": "agent-1",
  "action": "accept",                     // accept | reject | partial | withdraw (partial: phone source editor only)
  "wrapper_sha256": "<§10.3, of the wrapper the user decided>",
  "source_file": "docs-x/tex/source/a.tex",
  "decided_at": "2026-10-11T08:59:12.345Z",
  "origin": "desktop"                     // desktop | vscode | thoughtsctl | mcp | phone_editor
}
```

Transport: an optional member `proposal_decisions` (array, at most 500, unique `proposal_id`) on

- `SourcePublicationRequest` (`POST /v1/source-publications`, used by the desktop's `thoughts-publish-sources`): claims for the whole publication, so a decision followed by a move or rename before Sync still matches;
- `SourceApplyRequest` (`POST /v1/sources/apply`, used by the phone's source edit queue): claims for that path;
- the conflict resolution request (`POST /v1/conflicts/{conflict_id}/resolve`, the desktop's `source_conflict_resolution` outbox kind and the phone's equivalent): claims that were held back by a conflict (§10.8).

The claim is part of the request identity (the publication `request_sha256` and operation retries): a retry MUST send the same claims.
A server without capability `proposal_decisions_v1` ignores the member (unknown fields are dropped), which is harmless: such a server still classifies exact decisions itself (§10.9).

There is no separate decision endpoint and no server-side decision table. A claim exists only

1. in the client's durable outbox, next to the source upload it belongs to, and
2. for the duration of the server transaction that applies that upload.

It expires when the server answers the upload (any of `applied`, `merged`, `duplicate`), or when the client finds, at upload time, that the content it uploads for `source_file` has a valid wrapper or an issue carrying the claimed ID (the decision was undone locally). Claims wait for an upload that includes their `source_file` (an upsert, a deletion, or a rename's deletion half). A `conflict` answer keeps it for the resolving upload. So no decision history is kept anywhere.

Only a source the client synchronizes gets a claim: for the desktop, a file the source manifest lists or would list once it exists (a Project's folder, one of its source trees, not under `tex/generated/`, not excluded by `.ThoughtIgnore`; the publisher's discovery rule). A decision in any other file still edits the file but records no claim, since no upload could ever carry it and the server has no proposal row for it. A client MUST also drop, before an upload, every stored claim whose `source_file` is not (or no longer) such a source, or whose file no longer exists locally with no deletion left to upload, and log that it did.

#### 10.4.3 Matching (server)

Inside the source transaction, after the merge and before the transaction commits, for each claim `c` of the request:

1. If the reconciler sees `c.proposal_id` vanish in this transaction (§10.2), the row retires with the claim's status: `accept` → `accepted`, `reject` → `rejected`, `partial` → `decided_in_parts`, `withdraw` → `withdrawn`. Outcome `matched`. The claim is trusted as a record of an explicit decision; the resulting text is not compared with §7 (the same upload may carry other edits made after the decision).
2. Else, if the row is `removed_outside` and `c.wrapper_sha256` equals the row's `wrapper_sha256`: the decision was made on exactly the version that vanished earlier (an older client, another device or a hand edit uploaded the removal first). The row retires as in 1. Outcome `matched_late`.
3. Else, if the row is retired or does not exist: outcome `settled` (another device or the phone already decided; nothing changes).
4. Else (the wrapper is still in canonical source after the merge, or the removed version differs): outcome `unmatched`. Nothing changes; the claim is dropped.

A wrapper that vanishes in a transaction with no claim for it and no server-applied resolution becomes `removed_outside`.
Claims never create, change or restore proposals, and a claim for a wrapper that is not removed never removes it.

The upload response gains `proposal_decisions: [{"decision_id", "proposal_id", "outcome"}]` (`SourceApplyResult`; per publication in `SourcePublicationResult`). Clients MAY show `unmatched` in diagnostics; they MUST drop every answered claim.

### 10.5 What each client must do

All clients:

- MUST read `status` and show `removed_outside` rows under Issues, never as decidable proposals, and never drop them merely because the source no longer contains the wrapper.
- MUST NOT send operations that change `proposal` rows except Dismiss (§10.6).
- MUST attach a claim for every wrapper they remove through an explicit decision, and only then.
- MUST record the claim durably before writing the decided text (write-ahead), so a crash leaves either nothing or a claim whose wrapper is still present (dropped at upload).
- SHOULD warn when a plain text edit removes a whole wrapper ("This edit removes an AI proposal. Accept or reject it in Thoughts instead; if you save, it will be listed as removed outside Thoughts.").

Desktop: every local decision (`resolveLiveAgentProposedEdits`) and `remove-proposal` (`authorProposal`, which runs inside `thoughtsctl`) in a managed source (§10.4.2) stores its claims in the desktop sync database next to the pending path, in the same step that writes the `proposal_pending_*` journal and before the file is replaced. `thoughts-publish-sources` attaches the claims of every path it publishes, drops claims whose wrapper is present in the bytes it uploads, drops claims no upload can carry (§10.4.2), and deletes the published ones when the publication is answered. That database belongs to the default Library of the account's own data folder: a Library chosen with `THOUGHTS_HOME` outside a private `HOME`, `CFFIXED_USER_HOME` or Qt test mode has none, so tests never write the real one. `thoughtsctl decide-proposal` (§10.7.3) asks the app to run the same code. A local Undo (`restoreLiveAgentProposalSource`) brings the wrapper back and so cancels the claim at upload time (§10.4.2). Bundle-only decisions keep using the `agent_proposal_resolution` outbox (§10.4.1).

Phone: decisions from the PDF sheet and Overview stay server-applied. The source editor (`ProposalSourceActivity`) derives claims for a save from its review journal: every ID that is a valid wrapper in the save's base, is absent from the saved contents, and whose last not-undone journal event is a whole or partial decision. They travel in the `SourceEditQueue` request and its `POST /v1/sources/apply`.

VS Code: whole-proposal Accept and Reject only. They MUST go through `thoughtsctl decide-proposal`, like Delete Comment goes through `thoughtsctl delete-comment`: the buffer must be saved and unchanged, the app writes the file, the extension reloads it from disk. Partial decisions are removed from VS Code (the Accept/Reject Selection commands and the extension's use of `partialReview.js`); they remain a phone source-editor feature, which is the only producer of `partial` claims. The extension no longer edits the wrapper itself and no longer writes `comments/.history/proposal_events.d` (history is retired).

### 10.6 Dismiss and Restore Proposal

**Dismiss** retires a `removed_outside` row without touching any source: an ordinary client operation on the `proposal` entity with `base_revision` = the row's revision and the row's payload with `status: "dismissed"`, `kind: "dismissed"`, `deleted: true`. The server accepts a client operation on `proposal` only for this transition; otherwise it answers `conflict` ("The proposal is no longer removed outside Thoughts"), e.g. after a Restore on another device. Clients queue it offline like any operation. The row stays retired; if the wrapper reappears later it is `pending` again.

**Restore Proposal** puts the markup back with an ordinary local source edit, uploaded like any edit (desktop file write; phone `SourceEditQueue`, as `LocalSourceComments.restoreAnchor` does for comments). No proposal operation is sent: when the server sees the wrapper reappear it sets `pending`. Every client computes the edit with the same algorithm (fixtures: `decisions.json`, `restore`):

Input: the row's `snapshot`, `source_file`, `removal.source_line` (L), and the current text T of `source_file` (the client's copy, including unsynced edits).

1. If T has a valid wrapper with this ID: `already_present` (no edit; the row becomes `pending` with the next Sync).
2. If `source_file` does not exist: refuse `source_missing`.
3. If the ID occurs anywhere else in T as text (a broken wrapper, a comment): refuse `id_in_source` (the user repairs it).
4. Candidates are the occurrences of the non-empty texts among `after` (replacement) and `before` (original) in T that start at the beginning of a line, end at the end of a line (after an LF, or at end of file), and do not overlap a wrapper or an issue span (§6).
   Only if there is none and one of the two texts is empty (an insertion or a deletion proposal), the single candidate is the empty range at the start of line L (the end of T when T has fewer lines).
5. Pick the candidate whose first line is nearest to L. A tie between different candidates is refused `ambiguous`; no candidate is refused `text_changed` ("The proposed and the original text were both edited since the markup was removed; Thoughts cannot tell where the proposal belongs.").
6. Replace the candidate with a wrapper written per §8 from the snapshot: same ID, explanation, original, replacement, and metadata (`created_at`/`conversation_id` exactly as stored, and `conversation_url` when stored). A snapshot without both values cannot yield a valid wrapper and is refused `not_restorable` by step 7. A LaTeX explanation is written as stored (it is already TeX, §3.4), not escaped again. A Markdown proposal is always written as v2.
7. The client MUST re-parse the result and refuse `not_restorable` unless it yields exactly one valid proposal with this ID and the snapshot's fields, and no new issue.

Whichever text the candidate held, the restored proposal is undecided again: Accept yields `after`, Reject yields `before`.
A refused Restore leaves the row `removed_outside`; the UI shows the reason, the source location (file:L), the proposal's texts with Copy, and Dismiss.

### 10.7 Operations

#### 10.7.1 Server

- Capability `proposal_decisions_v1` (in `SERVER_CAPABILITIES`): the server reads claims, writes `removed_outside`, `wrapper_sha256`, `removal`, and accepts Dismiss.
- Setting `proposal_decisions_strict` (off at the first deploy, §10.9): when off, a vanished wrapper without claim whose `looks_like` is `accept` or `reject` is still retired as `accepted`/`rejected` (today's behaviour) instead of `removed_outside`.

#### 10.7.2 Clients' manifest and projection fields

- Desktop and phone read `status`, `wrapper_sha256`, `removal` from the `proposal` rows they already receive (`/v1/changes`, `/v1/projections`; current proposals are global by ID).
- The phone source bundle manifest is unchanged: removed proposals are not in `agent_proposals` (they are not in the source). The phone's `withCurrentProposals` overlay keeps hiding non-`pending` rows from the proposal list and adds `removed_outside` rows to Overview Issues.

#### 10.7.3 `thoughtsctl decide-proposal`

Same transport and conventions as `thoughtsctl delete-comment`: JSON request on stdin, `thoughtsctl` adds `command` and `schema_version: 1` and sends it to the running app over the command socket; the app executes the decision through its own path (`resolveLiveAgentProposedEdits`, claims included) and answers with one JSON object.

```json
{
  "request_id": "<uuid v4, reused on retry>",
  "source": "/absolute/path/to/a.tex",
  "expected_source_sha256": "<sha256 of the saved file the user looked at>",
  "proposal_id": "agent-1",
  "wrapper_sha256": "<§10.3, the wrapper the user looked at>",
  "action": "accept",
  "origin": "vscode"
}
```

- `action`: `accept` | `reject` only, a whole decision per §7. There are no partial decisions through `thoughtsctl`; any other action is refused `invalid_request`.
- Refusals (definitive): the spec code (§7) when the ID does not name one valid proposal; `source_changed` when the file's SHA-256 differs from `expected_source_sha256` or the wrapper's from `wrapper_sha256`; `not_in_library` when the file is not a Library source; `request_conflict` when `request_id` was used for a different request.
- Retryable, as for delete-comment and the card commands: `busy`, `transport_error`, `timeout`, `recovery_pending`. A retry with the same `request_id` after success returns the stored answer with `replayed: true` (the proposal-authoring replay store, `comments/.history/agent-requests.json`, 30 days).
- Success: `{"state": "accepted" | "rejected", "proposal_id": "agent-1", "source": "…", "source_sha256": "<after>", "claim": "recorded" | "not_applicable" | "not_recorded", "sync": "pending"}`. `claim` is `recorded` for a managed source, `not_applicable` when Sync does not manage the file (§10.4.2: the file is decided, no claim is kept) and `not_recorded` when the Library has no desktop sync database.
- MCP does not expose it: agents never decide; they may only withdraw their own proposal with `remove_proposal`. `thoughtsctl --help` says it is for editor integrations acting on a user's click.

### 10.8 Edge cases

- **Offline desktop.** Claims wait with the source change; nothing is decided server-side until the upload. Meanwhile the proposal is `pending` on other devices.
- **Upload before claim / claim before upload.** Cannot happen within one client (the claim is in the upload). Across clients: the removal reaches the server first without a claim (another device's hand edit, an old client) → `removed_outside`, then the deciding client's upload matches late (§10.4.3 rule 2).
- **Two devices decide.** Phone accepts on the server, desktop rejects offline: the desktop's upload conflicts or merges per the source merge rules; if it applies, its claim is `settled`. Two identical decisions merge cleanly and the second claim is `settled`.
- **Decision on an older version.** Another device changed the proposal while the desktop decided offline: the three-way merge conflicts on the wrapper, so nothing is applied, even when the two changes are on adjacent lines rather than the same ones; after the user resolves the conflict, a claim matches only if the resolved text removes the wrapper.
- **Edits next to a proposal.** A proposal added, changed or decided on one device next to lines edited on another merges cleanly when no line is changed by both and each wrapper comes out as on the side that changed it (docs/architecture.md).
- **Conflict.** Claims stay in the outbox and are sent with the conflict resolution, then expire with its answer.
- **Undo.** A local undo before upload cancels the claim (§10.4.2). After upload, bringing the wrapper back (desktop undo, phone undo of a resolution) makes it `pending`.
- **Restore after edits.** Restore needs the original or the replacement text, verbatim on whole lines; otherwise it refuses `text_changed` and offers Copy (the proposal's texts) and Dismiss; there is no "restore at the line anyway".
- **Restore while the proposal is retired elsewhere.** The wrapper reappears → `pending` (it was restored deliberately). A Dismiss queued on another device then conflicts and is dropped.
- **File moved by hand.** Non-atomic moves (delete in one upload, add in another) pass through `removed_outside` and come back `pending` on their own.
- **Agents editing files directly.** Removal by an agent's file edit or a build repair is "removed outside Thoughts" by design.
- **Several wrappers removed by one hand edit.** Each becomes its own `removed_outside` row; `looks_like` may be `accept` for a batch (§10.3).

### 10.9 Rollout and compatibility

1. **Server, compatible mode.** Ship claims, matching, `wrapper_sha256`, `removal`, `removed_outside`, Dismiss and the capability with `proposal_decisions_strict` off. Only removals that are not exact decisions (today's `deleted_from_source`) become `removed_outside`. Old clients are safe: the phone's projection overlay already hides every non-`pending` row, and the desktop derives proposals from sources and bundles and does not read server `proposal` rows at all. Old clients never send claims, and an old server ignores them.
2. **Clients.** Desktop (claims, Issues UI, Dismiss, Restore Proposal, `decide-proposal`), phone (editor claims, Issues UI, Dismiss, Restore Proposal), VS Code (`decide-proposal`). Clients may send claims to any server (an old one ignores them); they offer Dismiss only when the server has `proposal_decisions_v1`.
3. **Server, strict mode.** Turn `proposal_decisions_strict` on only after desktop, phone and VS Code builds that send claims (VS Code through `decide-proposal`) are installed. From then on only claims and server-applied resolutions decide.

### 10.10 Migration

- Pending proposals need no migration: they stay `pending`; the server backfills `wrapper_sha256` at the next reconciliation (or with a one-off `reconcile` run).
- Proposals already retired (`deleted_from_source`, or `accepted`/`rejected` by exact-text classification) stay retired. There is no revival path: only removals observed after the server ships phase 2 can become `removed_outside`.

## 11. Agent figures

Status: version 1 (2026-10-30). Server: `src/thoughts_server/agent_figures.py`; writer: `clients/thoughts-cli` (`thoughts_cli/figures.py`).

A proposal MAY add drawings. A drawing is an ordinary canonical **text** source, published in the same source publication as the proposal, so both arrive together or not at all:

```
<owner>/<tree>/source/[<dir>/]agent-figures/<name>.svg      tree: tex or markdown
```

- `<name>` matches `[a-z0-9][a-z0-9_-]{0,63}`; the folder is the folder of the note that uses it. Any other path is not an agent figure.
- The content is an SVG document of at most 1 MiB whose first line names the proposal that added it: `<!-- thoughts-agent-figure proposal="<id>" -->`. It MUST NOT declare a DOCTYPE or entities, contain `script`, `foreignObject`, `iframe`, `object`, `embed`, `audio` or `video`, event-handler attributes, `href`/`xlink:href` other than `#…` or `data:image/…`, or style `url()` other than `#…`/`data:image/…` or `@import`. The server refuses any publication that writes an agent figure violating this (`agent figure <path>: <reason>`), whoever sends it.
- The proposal's replacement references the figure: LaTeX `\includegraphics[...]{agent-figures/<name>}` (no extension), Markdown `![...](agent-figures/<name>.svg)`. The proposal ID is deliberately not part of the path or the reference: the ID of a decided proposal must occur in no note (§10.2), while an accepted reference stays.
- Rendering: Markdown reads the SVG. pdflatex cannot, so every build converts the figures of the document's TeX trees with `rsvg-convert` (fixed `SOURCE_DATE_EPOCH`, byte-identical output) to `<owner>/build/thoughts-agent-figures/<same path>.pdf` and puts the note's folder there on `TEXINPUTS`. A pending proposal therefore shows its figure in the PDF, Reject removes the reference, Accept keeps it. Compiled-component caches track the converted PDF, and a document's authored dependencies list the SVG.
- Clients: the figure is an authored source on the server only. The desktop does not install `.svg` sources and ignores them (it neither uploads them as build inputs nor deletes them); the phone shows the server's PDF. Neither needs to know about figures.
- Clean-up: the server worker deletes, hourly, every agent figure whose first line names a proposal that is `rejected`, `withdrawn`, `dismissed`, `document_deleted` or `decided_in_parts` for at least 7 days (so phone Undo still finds it) and whose `agent-figures/<name>` no `.tex`, `.md`, `.markdown` or `.sty` source mentions. Figures of `pending`, `removed_outside` (Restore) and `accepted` proposals stay.
- Writer (`thoughts-cli`, a thoughts-cli extension of the §8 requests): `figures: [{name, svg}]` on each entry of `create-proposals` and on `create-proposal` and `revise-proposal`. The writer refuses (`invalid_figure`) a figure the replacement does not reference, an invalid name or SVG, a duplicate name, a note outside a `tex/source` or `markdown/source` tree, and an existing figure path, except that `revise-proposal` may replace a figure its proposal added. It writes the first line itself (an XML declaration is dropped) and reports `figures: [{name, path, proposal_id, reference}]`.

## 12. Move pairs

Status: version 1 (2026-11-11). Writer: the desktop (`thoughtsctl move-card-passage`, the MCP tool `move_review_card` for a card linked to source markers). Server: `agent_proposals.py` (`_normal_candidates`, `_partner_source`), `proposal_history.reconcile_proposal_history`, `review_reanchor.cards_moved_by_proposals`; capability `review_card_move_pairs_v1`.

A review card linked to source markers is identified by its markers (`\ReviewCardMaskStart{<card>}{<segment>}%` … `\ReviewCardMaskEnd{…}%` lines in LaTeX, `<!-- thoughts:v1:start review:<card>:answer:<segment> -->` … `end` lines in Markdown), so moving its marked passage, markers included, keeps the card, its schedule and its history. An agent moves it with two ordinary proposals that the user decides as one:

| ID | where | `original` | `replacement` |
|---|---|---|---|
| `<base>.cut` | the card's source | the whole lines from its first marker line to its last | empty |
| `<base>.paste` | the destination, at a line boundary | empty | the same text (a final LF added when it had none) |

`<base>` is `agent-<uuid4>` (lowercase); the two IDs match `agent-[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\.(cut|paste)` and each names the other as its **partner**. Nothing else in the format changes: both are valid version 1 proposals that every reader parses as before (§3–§6), §7 decides each of them alone, and an old client shows them as two proposals. The pairing is a rule for the clients that decide.

Choice. Pairing by ID needs no change to the wrapper grammar, the fixtures or any parser, and keeps per-source proposals, claims (§10.4.2) and resolution jobs (§10.4.1) as they are. A metadata field would have made every installed reader report the wrappers as `invalid_metadata`; a single proposal spanning both places cannot cross files.

### 12.1 Deciding

- A decision that names one half decides its partner too, with the same action, in its own source if it is elsewhere. The two files are written together: the desktop through one journal that its recovery completes after a crash (`proposal_move_pending_*.json`), the server in one source publication (§10.4.1). Undo restores both.
- A half whose partner is not a valid pending proposal in exactly one source (deleted, removed outside Thoughts, decided apart by an old client) is not decided: refusal `move_incomplete`; when the partner is pending in several sources, `move_ambiguous`. The agent may still withdraw it.
- Withdrawing either half (`remove_proposal`) withdraws both; a lone half alone. A half cannot be revised (`move_proposal`): withdraw the move and make it again.
- Partial decisions of a half are refused (Android source editor). Phone decisions go through the server, which finds the partner by its current `proposal` row or, failing that, by searching the canonical sources; the phone sends only the half its document shows.
- Each half retires with the decision (§10.2, §10.4): a server-applied resolution covers the partners of its `proposal_ids`; a desktop decision sends a claim for each half.
- Explanations MUST NOT contain the partner's ID or the card ID: the partner's ID in text would keep a decided half from vanishing (§10.2), and a card ID outside its markers makes the desktop refuse to read the card's markers.

### 12.2 Writing

The writer refuses (nothing written) when the server lacks `review_card_move_pairs_v1` (`server_unsupported`: an older server would decide a phone's half alone); the card is unavailable, not linked to markers (`pdf_only_card`) or has markers in several sources; the destination has another format than the card's source (`format_mismatch`); its version is stale (`source_conflict`); the marked passage intersects a pending proposal (`proposal_overlap`) or holds only some of another card's markers (`split_card`; whole cards inside move along, `also_moved_card_ids`); the insertion line is inside a pending proposal or inside the passage itself (`invalid_range`; at the passage's own place `no_change`); after acceptance the card's markers would not read back at the destination, e.g. in a TeX preamble (`invalid_destination`); a link in the passage would not resolve from its new place (`invalid_link`, as §8 writers check). Generated sources are refused on either side (`generated_source`).

### 12.3 Rendering and cards

While the pair is pending, the PDFs show it as accepted, as for every proposal: the cut's markers are hidden with its original, the paste's are rendered with its replacement. The card therefore follows its markers to the destination document at its next build, and back after a rejection, exactly as after a cut and paste by hand. A card follows markers into another Project only when a move pair carries them (`cards_moved_by_proposals`: a `.paste` row whose `after` and its `.cut` partner's `before` both hold the card's start marker); a hand cut and paste stays within the Project.
